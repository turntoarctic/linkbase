# 90 - 执行计划

> 权威文档：阶段划分与任务分解。**本文不维护状态**——状态一律见 91。每个任务的验收标准是完成的唯一定义，不写逐步 bash 脚本（教训：旧版执行计划的可执行脚本与设计漂移后成了错误源头；代码细节以设计文档为准）。

## Phase 0：模型改造与技术验证（约 1 周）

目标：拆掉旧实体模型，搭好 BlockSuite 数据通路，跑通「注册 → 建页 → 写字 → 服务端落库 → 换端打开」的最小闭环。

| 任务 | 内容 | 验收标准 |
|------|------|----------|
| T0.1 拆除旧模块 | 删除 projects / requirements 前后端代码与路由、旧表（见 91 §2 拆除清单） | typecheck/test 全绿，无残留引用 |
| T0.2 vendor BlockSuite 源码 | 按 05 §2 把上游包迁入 `packages/blocksuite/`（含 `scripts/vendor-blocksuite.mjs` 与 tsconfig/scripts fixup），排除 playground/docs/integration-test | `bun install` 成功；web 里 `import '@blocksuite/affine/effects'` 类型与运行时均可用；生产构建可出产物 |
| T0.3 数据库重建 | 按 08 建 drizzle schema + 迁移（含 `CREATE EXTENSION pg_trgm`）；保留 users/workspaces 相关表并改造 | `bun run db:migrate` 全表与扩展建成；seed 能建空间+快速开始页 |
| T0.4 元数据提取验证 | 验证 05 §6 两方案（@blocksuite/store headless vs 纯 yjs 遍历），二选一回填 05 | 服务端能从 update 提取 title/纯文本/子页 id，单测覆盖 |
| T0.5 doc 通路 | 10 §5.2 两个二进制端点 + yjs merge/diff 工具（07 lib） | 接口测试：push 随机 update 后 pull（带旧 state vector）能取回差异；空页 404 |
| T0.6 页面 API | 10 §4 页面 CRUD + 回收站端点 | register→create page→trash→restore 全链接口测试通过 |
| T0.7 认证全流程与零仪式首屏 | 注册/登录/刷新/登出闭环（07 §5、10 §2）+ 注册后自动建空间与快速开始页并直接进编辑器（01 §2.1） | P0-1/P0-2：token 刷新无感；新用户注册后无任何建容器步骤即可输入 |
| T0.8 i18n 基础设施 | i18next 接入 + zh-CN/en 资源骨架（命名空间 common/auth/workspace/editor/errors）+ 错误码映射 + 守护脚本（无硬编码/key 对齐，13 §7） | P0-14：登录页双语可切换并持久化；登录后文案随 `users.locale`；脚本全绿 |
| T0.9 BlockSuite i18n 桥接清单验证 | 核对 vendored 0.22.4：哪些内置 UI 字符串可经扩展点覆盖、哪些必须改源码，产出清单回填 13 §5 | 清单落地（分「可覆盖/须改源码/放弃」三类），作为 P1-8 工作量依据 |
